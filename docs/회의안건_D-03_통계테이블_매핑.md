# 회의 안건 — 통계 테이블 매핑 (`period_stats` ↔ `mart_daily_posture`)

> 작성: 2026-10-04 · 관련 작업: D-03(통계 집계 쿼리), D-05(Spark 배치) · PRD 7절 미결정 #4, FR-BE-14/15
> 참석 필요: DB 담당, 데이터(Spark) 담당, BE 담당(DevOps/BE), FE 담당(조회 화면 지표 확인)

> **2026-10-05 추가**: 팀 저장소 `develop` 브랜치에 DB 담당의 스키마 V0.3(`posture_service`, 17개 테이블)이 있고,
> 일별 통계 테이블 **`daily_stat`**(PK `user_account_id`+`stat_date`, 초 단위 `valid_sec`/`good_sec`, `event_count`, `computed_at`,
> 세션 시작 날짜 귀속)이 이미 정의돼 있다. 안건 1·2·3·5·7은 V0.3에 사실상 답이 있으므로, 회의는 **"V0.3 `daily_stat`을 기준으로 채택할지,
> 우리 `posture_app`·v4 `mart_daily_posture`를 어떻게 맞출지"**로 좁힐 수 있다. 상세는 `팀저장소_분석_2026-10-05.md` 6장, 컬럼 단위 비교와 V0.3 채택 시 BE 변경 사항은 **`회의자료_DB스키마_매핑표.md`**.
> 같은 저장소의 `jin_app` 브랜치에는 또 다른 스키마(Flyway V1)가 있어, DB 스키마가 세 갈래로 나뉜 상태다.

## 0. 회의 목적

D-03(기간 통계를 채우는 집계)을 시작하려면 **어느 테이블에, 어떤 단위로, 어떤 지표를, 누가 채우는지**가 먼저 정해져야 한다.
현재 DB에는 `period_stats`(스키마만 있고 비어 있음)가 있고, v4 설계는 `mart_daily_posture`(Spark J3가 매일 채움)를 목표로 한다.
이 회의에서 아래 안건을 확정하면 D-03을 바로 착수할 수 있다.

## 1. 현재와 목표 비교

| 구분 | 현재 `period_stats` | v4 `mart_daily_posture` |
|---|---|---|
| 집계 단위 | 임의 기간 (`period_start` ~ `period_end`) | 사용자 × 하루 (`user_id`, `date`) |
| 시간 단위 | 초 (`DOUBLE`) | 밀리초 (`total_ms`, `bad_ms` 등) |
| 중복 방지 키 | 없음 (`id` AUTO_INCREMENT, 일반 인덱스만) | 명시 안 됨 (`user_id, date`가 자연키) |
| 작성 주체 | 미정 (스케줄 쿼리 또는 Spark) | Spark J3, 매일 03:00, JDBC |
| 원천 데이터 | 미정 | HDFS `/data/raw/episodes` (`posture.episodes` 토픽 적재분) |
| 데이터 상태 | 비어 있음 → 이름·구조 변경 부담 없음 | 아직 없음 |

### 지표 대응표

| `period_stats` | `mart_daily_posture` | 비고 |
|---|---|---|
| `valid_seconds` | `total_ms` | 측정 총 시간. **원천을 무엇으로 볼지** 정해야 함 (안건 4) |
| `normal_ratio` | (없음) | `1 − bad_ms / total_ms`로 계산 가능 → 저장할지, 조회 시 계산할지 |
| — | `bad_ms` | **정의 필요** (안건 4) |
| `collapse_count` | `episode_count` | 같은 의미 |
| `collapse_per_hour` | (없음) | `episode_count / (total_ms/3,600,000)`으로 계산 가능 |
| `avg_duration_seconds` | `avg_episode_ms` | 같은 의미, 단위만 다름 |
| `median_duration_seconds` | (없음) | 마트에 추가할지 (Spark `percentile_approx`로 계산 가능) |
| `model_version` | (없음) | 모델 버전별 비교가 필요하면 추가 (안건 6) |
| `computed_at` | (없음) | 재집계 추적용으로 추가 권장 |

## 2. 안건 목록

### 안건 1. 테이블 이름과 존치 여부
- (A) `mart_daily_posture`로 통일하고 `period_stats`는 삭제
- (B) 둘 다 둠 — 마트는 일 단위 원천, `period_stats`는 주·월 등 임의 기간 롤업용
- (C) `period_stats` 이름 유지, 구조만 일 단위로 변경
- **BE 제안: (A)** — v4 문서·PRD·Spark J3가 모두 이 이름을 쓰고, `period_stats`는 비어 있어 삭제 부담이 없다. 주·월 통계는 조회 API에서 일 단위를 합산한다.

### 안건 2. 집계 단위와 날짜 기준
- 집계 단위를 **사용자 × 하루**로 확정할지
- `date`의 기준 시간대: **KST(Asia/Seoul)** vs UTC — 메시지 시각은 epoch ms(UTC), DB 접속은 `serverTimezone=Asia/Seoul`
- 자정을 넘긴 에피소드·세션: 시작일에 전부 귀속 vs 날짜별로 시간을 나눠 귀속
- **BE 제안**: KST 기준, 자정 걸친 세션·에피소드는 시작일 귀속(단순, 시연 데이터에 영향 거의 없음)

### 안건 3. 시간 단위
- 초(`DOUBLE`) vs 밀리초(`BIGINT`)
- 현재 `collapse_events.duration_seconds`는 초, v4 `episodes.duration_ms`·메시지 `durationMs`는 밀리초
- **BE 제안**: 밀리초(`BIGINT`)로 통일 — 메시지 규격과 같아 변환 오류가 없다

### 안건 4. `total_ms` / `bad_ms`의 정의와 원천
- `total_ms`(측정 시간): 세션의 (`ended_at` 또는 `last_seen_at`) − `started_at` 합계 vs `SESSION_SUMMARY.totalMs`
- `bad_ms`(나쁜 자세 시간): **확정된 에피소드 지속시간 합**(T1 이상 지속된 구간만) vs **추론 결과가 bad였던 시간 전체**
  - 두 정의는 값이 다르다. 전자는 "알림 대상이 된 시간", 후자는 "모델이 나쁘다고 본 시간"
- 연구 지표(바른 자세 유지율, ABA 비교)에서 어느 쪽을 쓸지 — ML/연구 담당 의견 필요
- **BE 제안**: `bad_ms` = 확정 에피소드 지속시간 합 (현재 저장된 데이터로 바로 계산 가능). 추론 bad 시간 전체가 필요하면 별도 컬럼으로 추가

### 안건 5. 추가 컬럼
- `median_episode_ms` 추가 여부 (현재 `period_stats`에 중앙값이 있음 — 계획서 "주기 분석" 지표)
- `normal_ratio`, `episodes_per_hour`를 저장할지, 조회 시 계산할지
- `computed_at`(집계 시각) 추가 여부
- **BE 제안**: 중앙값·`computed_at`은 저장, 비율·시간당 횟수는 조회 시 계산(원천 값에서 언제든 다시 구할 수 있음)

### 안건 6. 모델 버전 구분
- 같은 날 모델 버전이 바뀌면 통계를 나눌지
- 나눈다면 키가 (`user_id`, `date`, `model_version`)이 됨 → 조회 시 합산 필요
- **BE 제안**: 시연·실험 기간에는 버전 교체가 드물어 일 단위 키 유지, `model_version`은 "그날 주로 쓰인 버전"을 참고값으로만 저장 — ML 담당이 버전별 비교가 꼭 필요하다고 하면 키에 포함

### 안건 7. 중복 방지와 재집계 방식
- (`user_id`, `date`) UNIQUE 키를 걸고 upsert vs 해당 날짜 행 삭제 후 다시 삽입
- 배치가 실패하거나 원천이 늦게 들어왔을 때 같은 날짜를 다시 돌려도 결과가 같아야 함
- **BE 제안**: UNIQUE 키 + `INSERT ... ON DUPLICATE KEY UPDATE` (Spark J3도 같은 키로 덮어쓰기)

### 안건 8. 진행 중 데이터 처리
- 아직 끝나지 않은 세션(`status=ACTIVE`)과 에피소드(`ongoing=1`)를 그날 집계에 넣을지
- "오늘" 통계를 화면에 실시간으로 보여줄지 — 마트는 다음 날 새벽 확정이므로, 오늘 값은 원천 테이블을 직접 조회해야 함
- **BE 제안**: 마트는 종료된 것만 집계. 오늘 값이 필요하면 조회 API가 원천에서 바로 계산(FE 담당 확인 필요)

### 안건 9. 누가, 언제, 어떤 원천으로 채우나 (단계 전환)
- v4 목표 경로: `posture.episodes` 토픽 → HDFS → Spark J3 → 마트. 그러나 `posture.episodes` 발행(FR-BE-05)과 Spark J1/J3(D-05)가 아직 없음
- 제안 단계:
  1. **지금(D-03)**: api-server 스케줄러가 MySQL `sessions` + `collapse_events`를 SQL로 집계해 마트를 채움 (매일 03:00, 수동 실행 API 포함)
  2. **이후(D-05)**: Spark J3가 같은 테이블·같은 키·같은 정의로 대체 → 1단계 스케줄러 끔
- 확인할 점: 1→2 전환 시 값이 같게 나오도록 **안건 4의 정의를 문서로 고정**

### 안건 10. 연관 매핑 (같이 정하면 좋은 것)
마트의 원천이 되는 테이블도 v4와 이름·구조가 다르다. 이번 회의에서 방침만이라도 정한다.

| 현재 | v4 목표 | 차이 |
|---|---|---|
| `collapse_events` | `episodes` | v4에 `event_id`(UNIQUE), `max_prob`, `model_version`, `duration_ms` 추가 / 현재 `recovered`, `ongoing`, `last_alert_at` 있음 |
| `sessions` | `sessions` | v4에 `total_ms`, `bad_ms`, `ended_at` / 현재 `last_seen_at`, `sample_count`, `status` |
| `accounts` | `users` | 인증(D-07)과 함께 |
| `baseline_postures` | `baselines` | 캘리브레이션 API(FR-BE-11)와 함께 |

### 안건 11. 조회 API 요구 (FE 확인)
- 기록 화면에 필요한 지표: 일별 측정 시간, 나쁜 자세 시간·비율, 에피소드 횟수, 평균·중앙 지속시간, 주별 추이
- 조회 범위(최근 7일 / 30일 / 기간 지정)와 응답 형식
