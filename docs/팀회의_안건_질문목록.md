> 각 질문의 "BE 제안"은 논의 출발점일 뿐이며, 결정은 회의에서 합니다.

## 배경 (회의 전 1분 공유)

- 같은 기능(세션·판정·저장)이 두 갈래로 만들어지고 있습니다.
  - 우리 저장소 `dockerized-bigdata-env`: Kafka → 추론 → 상태머신(+Redis) → MySQL. 서버 PC에서 동작 검증 완료
  - 팀 저장소 `jin_app` 브랜치: REST → 추론 → Esper CEP → MySQL. 동기 HTTP, Kafka 없음
- DB 스키마는 세 갈래입니다: 우리 `posture_app` / 팀 `develop`의 V0.3(DB 담당) / `jin_app`의 Flyway V1
- 판정 시간·임계값도 FE, 우리 서버, V0.3 시드, v4 문서가 서로 다릅니다.
- 그래서 아래 질문이 정해지기 전에는 WebSocket, 토픽 전환, 통계 집계 작업을 시작할 수 없습니다.

## 1. 큰 방향 (가장 먼저)

**Q1. 서비스의 기준 백엔드는 어느 쪽으로 하나요?**
- (A) 아키텍처 v4 / 우리 저장소 기준. `jin_app` FE의 서버 연결 코드를 우리 API에 맞춤
- (B) `jin_app` 백엔드 기준. 우리 저장소는 인프라와 빅데이터(Kafka·HDFS·Spark)만 담당
- (C) 혼합. `jin_app`의 API 형식은 유지하고, 내부 연결을 Kafka로 바꿈
- BE 제안: A 또는 C. 계획서와 v4가 Kafka·HDFS·Spark를 요구하는데, B는 이 경로를 따로 붙여야 합니다.

**Q2. 두 저장소를 언제, 어떤 구조로 합치나요?**
- 우리 저장소를 팀 저장소의 어느 폴더에 넣을지 (`backend/`, `infra/` 등)
- 기준 브랜치는 `develop`인지. 개인 브랜치(`jin_app`, `lee_app1`, `lee_dev4`, `goodpose-mdweb`)는 어떤 순서로 병합할지
- CI/CD(D-09)는 병합 후 팀 저장소의 `make check`·`harness.yml`에 맞춰 다시 구성합니다.

**Q3. Spring Boot / Java 버전을 하나로 정할 수 있나요?**
- `jin_app`: Spring Boot 3.5 / Java 21, 우리: Spring Boot 4.0 / Java 17
- BE 제안: 병합하는 쪽 기준으로 통일. 병합 전에는 각자 유지

## 2. 실시간 데이터 흐름

**Q4. FE는 서버에 어떤 방식으로 보내나요?**
- (A) REST, 1초 단위, 판정 결과를 응답으로 즉시 받음 (`jin_app` 방식)
- (B) WebSocket, 0.5초 단위, 알림을 서버가 push (v4 방식)
- 참고: 우리 서버는 Kafka를 거치는 비동기 처리라서, REST 응답에 판정 결과를 바로 담을 수 없습니다. A를 택하면 FE가 결과를 다시 조회(GET)해야 합니다.
- BE 제안: 단기에는 REST(전송) + 조회(GET)로 연결하고, WebSocket(FR-BE-02)은 다음 단계에서 진행

**Q5. FE가 보내는 데이터는 무엇인가요?**
- (A) 변화량 3개 + 품질. 브라우저가 계산 (지금 FE와 `jin_app` 방식)
- (B) 원시 키포인트 33관절. 서버나 추론에서 계산 (v4 방식)
- 모델 담당에게: LSTM 입력이 키포인트 원본인지, 변화량인지
- BE 제안: 모델 입력이 정해질 때까지 A. 바꿀 때 메시지 규격의 `schemaVersion`을 올림

**Q6. 키포인트 추출 모델, fps, 전송 주기를 확정할 수 있나요?**
- 현재 FE: MediaPipe Pose **Lite**, GPU 30fps / CPU 20fps 상한, 수집은 최대 10Hz
- v4 초안: MediaPipe Pose 33, 15fps, 0.5초 묶음
- 이 값에 따라 서버 처리량 기준(NFR-02)이 바뀝니다. 지금은 10Hz로 동시 10명이 검증돼 있고, v4 주기로는 약 40명분입니다.

**Q7. LSTM 윈도우 크기와 stride는 얼마인가요?** (모델 담당)
- v4 초안: 3초(45프레임) / 0.5초

**Q8. 기준 자세가 없는 사용자의 측정 요청은 어떻게 처리하나요?**
- 초안: 추론을 건너뛰고 FE에 캘리브레이션을 요청

## 3. 판정 정책

**Q9. 판정 엔진은 어느 쪽을 쓰나요?**
- (A) Esper 별도 서비스 (`jin_app`)
- (B) 서버 안의 상태머신 + Redis 상태 저장 (우리 저장소)
- 참고: 9/30에 서버 메모리 문제로 Esper를 쓰지 않기로 결정했습니다(DN-18). B는 재시작 복원과 동시 10명 처리량까지 검증됐습니다.
- BE 제안: B

**Q10. 판정 파라미터 기본값을 하나로 정할 수 있나요?**

| 출처 | 임계값 | 지속 T1 | 회복 T2 | 재알림 T3 | 시간당 알림 상한 |
|---|---|---|---|---|---|
| FE `main` / `jin_app` | 0.7 | 3초 | 2초 | 60초 | 없음 |
| 우리 서버 (검증값) | — | 3초 | 3초 | 60초 | 없음 |
| V0.3 시드 `DEFAULT_TEMP` | 0.5 | 3초 | 2초 | 30초 | 12회 |
| v4 초안 | 0.5 | 10초 | 5초 | 60초 | — |

- 정한 값은 V0.3의 `threshold_policy` 테이블에 넣고, 서버는 그 테이블에서 읽도록 바꾸는 것을 제안합니다.

**Q11. "시간당 알림 상한"(V0.3의 `notify_max_per_hour`)을 도입하나요?** 도입한다면 상한에 걸린 알림은 기록만 하나요?

**Q12. 일시정지, 자리 비움, 측정 불가는 누가 판단하나요?** (FE / 추론 / 판정 엔진)
- V0.3에는 `excluded_interval` 테이블(PAUSE / ABSENCE / UNMEASURABLE)이 있지만, 지금 판정 엔진에는 이 개념이 없습니다.

## 4. DB 스키마

**Q13. 서비스 DB의 기준 스키마를 V0.3(`posture_service`, DB 담당)으로 정하나요?**
- 정하면 우리 `posture_app`과 `jin_app` Flyway V1은 V0.3에 맞춰 바꾸거나 폐기합니다.
- BE 제안: V0.3 채택. 측정값마다 DB에 쓰지 않는 구조라 지금 겪는 DB 쓰기 병목에도 유리합니다.

**Q14. 세션의 "마지막 수신 시각"은 어디에 두나요?**
- V0.3 `monitor_session`에는 이 컬럼이 없지만, 지금 서버의 "5분 무응답 세션 자동 종료"에 필요합니다.
- (A) 컬럼 추가를 DB 담당에게 요청 (B) Redis `session:{sessionId}`에 저장 (v4 설계)
- BE 제안: B

**Q15. 세션을 시작할 때 FE가 서버에 보내야 하는 값을 확정할 수 있나요?**
- V0.3 `monitor_session`은 장치(`capture_device`), 기준 자세, 판정 정책, 모델 버전, 화면 해상도, 알림 사용 여부를 필수로 요구합니다.
- 장치 식별값(`browser_device_key`)은 FE가 어떻게 만드나요?

**Q16. 인증을 붙이기 전까지 사용자는 어떻게 구분하나요?**
- 지금 클라이언트는 사용자 ID를 자유 문자열(`P01` 등)로 보내고, V0.3은 숫자 계정 ID를 요구합니다.
- BE 제안: 테스트 계정을 시드로 만들어 문자열과 연결해 두고, 인증 작업(D-07) 때 로그인 사용자 기준으로 바꿉니다.

**Q17. 인증 방식은 무엇으로 하나요?**
- (A) Spring Security 세션 + CSRF (`jin_app`) (B) Gateway + JWT (v4)

## 5. 통계 (D-03)

**Q18. 일별 통계 테이블은 V0.3의 `daily_stat`으로 정하나요?**
- 정하면 기존 안건 대부분(테이블 이름, 날짜 귀속, 단위, 중복 방지 키)은 V0.3을 따릅니다. 기준은 세션 시작 날짜, 초 단위, PK(사용자, 날짜)입니다.
- v4 문서의 `mart_daily_posture`는 이름만 `daily_stat`으로 바꿔 부릅니다.

**Q19. 통계 날짜의 기준 시간대(`STAT_TIMEZONE`)는 KST인가요?**

**Q20. "바른 자세 시간"(`good_sec`)과 "나쁜 자세 시간"은 정확히 무엇을 세나요?** (ML/연구 담당 의견 필요)
- (A) 확정된 붕괴 이벤트의 지속 시간만 뺌 (알림 대상이 된 시간)
- (B) 모델이 나쁘다고 본 시간을 전부 셈
- ABA 실험에서 쓰는 "바른 자세 유지율"과 같은 정의여야 합니다.

**Q21. 붕괴 지속시간의 평균과 중앙값을 `daily_stat`에 컬럼으로 추가하나요?** 아니면 조회할 때 계산하나요? (계획서 "주기 분석" 지표)

**Q22. "오늘" 통계도 화면에 보여주나요?**
- 일별 통계는 다음 날 새벽 배치로 확정되므로, 오늘 값은 원천 테이블에서 바로 계산해야 합니다.

**Q23. 통계는 누가, 어떤 순서로 채우나요?**
- BE 제안: 지금은 서버 스케줄러가 MySQL SQL로 집계하고, Spark J3(D-05)가 준비되면 같은 테이블·같은 정의로 교체합니다.

**Q24. FE 기록 화면에 필요한 지표와 조회 범위는 무엇인가요?** (FE 담당)
- 예: 일별 측정 시간, 바른 자세 비율, 붕괴 횟수, 평균 지속시간, 주별 추이 / 최근 7일·30일·기간 지정
