자세 분석 플랫폼 아키텍처 v4

2026-10-02기준 문서: 전체 설계안 v4 · 아키텍처 v4.0 · Kafka 메시지 규격 v1.0

서버 PC 한 대가 내부를 이루고, 사용자 브라우저·모델 담당자의 GPU PC·MySQL이 외부에 있습니다. 데이터는 실시간 경로와 적재·분석 경로로 나뉘고, 두 경로는 Kafka에서 갈라집니다.

내부 = 서버 PC 1대Ubuntu Server, 6코어 12스레드, 16GB. Spring 서비스와 Kafka·Redis·HDFS·Spark를 Docker Compose로 실행
외부 = 3곳사용자 브라우저, 외부 GPU PC(추론 + 학습), 외부 MySQL
경계를 넘는 포트 4종8080(앱 진입) · 9094(Kafka, GPU PC 전용) · 9870/9864(HDFS, GPU PC 전용) · 3306(MySQL로 나가는 연결)
지연 목표 1초 이내실시간 경로 예상 약 0.6초. HDFS·Spark는 실시간 경로에 없음

파이프라인 강조

전체 구성. 위 버튼으로 파이프라인을 고르면 그 흐름에 쓰이는 구성요소만 강조됩니다.

경계

경계를 넘는 연결은 이것뿐

내부 서비스끼리는 Docker 네트워크의 서비스 이름으로 통신하고, 외부와는 아래 다섯 개 연결만 엽니다.

연결방향포트허용 대상오가는 것
브라우저 → API gateway들어옴8080LAN 전체REST(로그인·캘리브레이션·기록), WebSocket(키포인트·알림)
GPU PC ↔ Kafka들어옴9094GPU PC IP만keypoints·baselines 소비, inference 발행
GPU PC ↔ HDFS들어옴9870, 9864GPU PC IP만학습셋 읽기, 모델 /models/v{n} 업로드
서버 PC → MySQL나감3306user·report·Spark J3회원, 기준자세 원본, 에피소드 기록, 통계 마트
팀원 → 서버 PC들어옴22SSH 키 인증만운영·배포
Redis, Kafka 9092, Spark UI 4040내부 전용127.0.0.1서버 PC 안외부 확인이 필요하면 SSH 터널

왜 이렇게 나눴나

  • GPU PC가 붙는 곳을 Kafka 9094 하나로 좁혔습니다. 추론 서비스는 Redis와 MySQL을 몰라도 됩니다(기준자세는 compacted 토픽으로 전달).
  • 실시간 경로가 경계를 넘는 곳은 8080과 9094 두 군데뿐입니다. 나머지 실시간 처리는 서버 PC 안에서 끝납니다.
  • MySQL을 밖에 두어 서버 PC를 재설치하거나 장애가 나도 영속 데이터는 남습니다.

설정할 때 주의

  • Docker가 연 포트는 ufw를 우회합니다. 내부 전용은 127.0.0.1:로 바인딩하고, GPU PC 전용 포트는 DOCKER-USER 체인에서 IP를 제한합니다.
  • Kafka에 EXTERNAL://<서버IP>:9094 리스너를 추가합니다. 컨테이너끼리는 kafka:19092를 씁니다.
  • GPU PC hosts 파일에 <서버IP> namenode datanode를 넣어야 WebHDFS 리다이렉트가 동작합니다.

파이프라인

데이터가 흐르는 다섯 갈래

실시간 경로 하나, 적재·분석 경로 셋, 그리고 사용자당 한 번 일어나는 캘리브레이션입니다. 각 카드의 단계는 실제 처리 순서입니다.

캘리브레이션

요청·이벤트사용자당 1회, 재측정 시 반복
  1. FE가 정자세 약 5초 분량의 키포인트를 측정해 POST /api/baselines로 보냅니다.
  2. gateway가 JWT를 확인하고 user-service로 넘깁니다.
  3. user-service가 관절별 평균·표준편차를 계산해 MySQL baselines에 저장합니다(version +1).
  4. 같은 값을 posture.baselines(compacted, key=userId)에 발행합니다.
  5. 추론 서비스가 토픽을 구독하다가 메모리 캐시를 갱신합니다.

왜 이 방식인가

기준값은 작고 반드시 남아야 하는 데이터라 스트림이 아니라 REST로 받고 MySQL에 원본을 둡니다. 추론 쪽에는 Kafka 복제본만 전달합니다.

회원 탈퇴

MySQL 삭제와 함께 같은 키로 value가 null인 tombstone을 발행하면 토픽에서도 지워집니다.

실시간 판정

실시간 경로사용자당 0.5초마다 · 목표 지연 1초 이내
  1. FE가 15fps로 키포인트를 뽑아 0.5초 분량씩 묶어 WebSocket으로 보냅니다.
  2. realtime-service가 형식을 검증하고 posture.keypoints에 발행합니다. 키가 userId라 사용자별 순서가 보장됩니다.
  3. GPU PC의 추론 서비스가 사용자·세션별로 3초 윈도우를 채우고, 0.5초마다 LSTM으로 good/bad를 분류해 posture.inference에 발행합니다.
  4. realtime-service가 결과로 Redis의 상태머신을 갱신합니다.
  5. 알림이 필요하면 Redis Pub/Sub으로 사용자가 연결된 인스턴스에 전달해 WebSocket으로 푸시하고, posture.episodes를 발행합니다. report-service가 이를 받아 MySQL에 기록합니다.

상태머신 (알림은 이걸로 판단)

NORMAL→SUSPECTT1 10초→BAD→RECOVERINGT2 5초→NORMAL

BAD 상태에서는 T3(60초)마다 재알림. 순간적인 오판정 하나로 알림이 울리지 않습니다.

GPU PC가 멈추면

5초간 결과가 없으면 FE에 “분석 일시 중단”을 표시합니다. 같은 추론 이미지를 서버 PC에서 CPU로 띄우고 Kafka 주소만 kafka:19092로 바꿉니다.

적재

적재·분석 경로매시간 · Spark J1
  1. cron이 docker exec spark spark-submit으로 J1을 실행합니다.
  2. J1이 keypoints·inference·episodes 세 토픽을 지난번 체크포인트 이후 오프셋부터 읽습니다.
  3. HDFS /data/raw/<토픽>/dt=…/hour=…/에 Parquet로 씁니다.
  4. 체크포인트를 갱신하고 종료합니다.

왜 availableNow인가

Structured Streaming을 쌓인 데이터만 처리하고 끝나게 실행합니다. Spark가 상주하지 않아 메모리를 잡 실행 중에만 쓰고, 오프셋은 체크포인트가 관리해 중복·누락이 없습니다.

실패하면

Kafka 보존 기간이 48시간이라 그 안에 다시 실행하면 체크포인트부터 이어서 적재합니다. 실시간 판정에는 영향이 없습니다.

학습 · 모델 배포

적재·분석 경로매일 02:00 또는 수동 · Spark J2 + GPU PC
  1. Spark J2가 원본 키포인트를 정제·윈도우 분할하고 라벨과 결합해 /data/curated/train/v{n}/을 만듭니다.
  2. GPU PC 학습 환경이 WebHDFS로 학습셋을 읽어 LSTM을 학습·검증합니다.
  3. 모델 파일과 meta.json을 /models/v{n}/에 올리고 MySQL model_versions에 등록합니다.
  4. 추론 서비스가 같은 PC의 로컬 모델 파일을 새 버전으로 교체해 불러옵니다.
  5. 이후 추론 결과에는 modelVersion: "v{n}"이 붙어 에피소드 기록까지 추적됩니다.

버전 규칙

모델 버전 v{n} = HDFS 경로 = 메시지의 modelVersion = MySQL model_versions. 어떤 판정이 어떤 모델에서 나왔는지 끝까지 따라갈 수 있습니다.

배포 형태

추론 서비스는 Dockerfile과 requirements.txt를 반드시 남깁니다. 서버 PC 대체 실행과 K8s Node 2 배포에 그대로 씁니다.

통계 마트

적재·분석 경로매일 03:00 · Spark J3
  1. Spark J3가 HDFS /data/raw/episodes를 읽어 사용자·일 단위로 집계합니다.
  2. JDBC로 MySQL mart_daily_posture에 씁니다.
  3. report-service가 마트를 SQL로 조회해 통계 API로 제공합니다.
  4. FE 기록 화면이 gateway를 거쳐 이 API를 호출합니다.

기록과 통계의 차이

개별 에피소드는 report-service가 Kafka에서 바로 받아 저장하므로 즉시 보입니다. 일별·주별 통계만 J3 배치를 거칩니다.

시연 중 주의

J2·J3는 CPU·메모리를 많이 쓰므로 시연 시간에는 실행하지 않습니다. Spark는 local[4]로 제한해 실시간 처리용 CPU를 남깁니다.
